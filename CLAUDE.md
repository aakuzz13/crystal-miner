# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo contains a Russian-language HTML5 idle/clicker game, **"Кристальная Шахта"**, in the style of Cookie Clicker. There is no build system, no package manager. Multiple versions of the game coexist side by side:

- `versions/miner-clicker-v2.html` — Cookie-Clicker-style version. Self-contained: HTML + inline `<style>` + inline `<script>`, no external assets besides a Google Fonts import (`Cinzel`). Frozen — do not edit.
- `versions/miner-clicker-v3.html` — current version, redesigned around an Inscryption-inspired art direction (etched linework, parchment cards, wax-seal rarity marks, illustrated per-location scenes) with a gacha chest/reel mechanic layered on top of the same base economy as v2. No grain/vignette overlay — an earlier pass had one, it was removed for being too dark/noisy. Fully self-contained: all third-party sprites/sounds are embedded as base64 (`SPRITES`/`SOUNDS` objects near the top of the `<script>`), so the file works standalone — double-click, `file://`, GitHub Pages, no server, no sibling `assets/` folder required.
- `assets/sprites/`, `assets/sounds/` — the *source* CC0 assets (Kenney.nl) that got embedded into v3. Not read at runtime by the shipped HTML; kept as the editable originals. See `docs/credits.md` for what's from where and its license, and "Updating v3's embedded assets" below for how to re-embed after changing a file here.
- `docs/credits.md` — asset attribution/licensing ledger; update it whenever a new third-party asset is added.

## Running / testing

There is no build step. Both v2 and v3 are fully self-contained — just open the file directly in a browser (double-click, or `file://...`). A local server also works if you prefer it:

```
python3 -m http.server 8000
```

then visit `http://localhost:8000/versions/miner-clicker-v3.html` (or `miner-clicker-v2.html`). There are no automated tests or linters configured — verify changes manually in a browser. Playwright + a pre-installed Chromium are available in this environment for scripted browser checks (see the `run` skill) if you need to verify interactions headlessly — note the gacha chest has a CSS bob animation, so Playwright needs `click({force: true})` on `#chest`, and forcing a specific gacha outcome for testing means overriding `Math.random` via `page.addInitScript` (be aware `generateLocationTexture()` and `generateLocationArt()` use a seeded `mulberry32` PRNG, not `Math.random`, specifically so they don't consume calls from the global random stream).

### Updating v3's embedded assets

If you change or add a file under `assets/sprites/` or `assets/sounds/` that v3 uses, the `SPRITES`/`SOUNDS` base64 blobs in `miner-clicker-v3.html` do **not** update themselves — there's no build step watching the folder. Re-embed manually, e.g. with a short Python snippet that `base64.b64encode()`s the file and replaces the corresponding entry in the `SPRITES`/`SOUNDS` object literal (`SPRITES` values are `data:image/png;base64,...` URIs assigned straight to `<img>.src`; `SOUNDS` values are raw base64, decoded via `b64ToArrayBuffer()` + `decodeAudioData` — no data URI prefix). Forgetting this step means the HTML keeps shipping the old asset even though the source file under `assets/` changed.

## Architecture (shared by v2 and v3)

Everything lives in one IIFE inside the `<script>` tag at the bottom of each version's HTML file. Key pieces, in order:

- **State**: a single `state` object persisted to `localStorage` under `SAVE_KEY` via `save()`/`load()`. v2 and v3 use different `SAVE_KEY` values so progress never crosses versions. A separate `SAVE_KEY + "_ts"` timestamp computes offline progress on load (`applyOfflineProgress()`, capped at 4 hours).
- **Static game data**: `clickUpgrade` (the pickaxe upgrade), `autoDefs` (array of 4 auto-miner definitions with cost/rate/rarity), `LOCATIONS` (array of 5 unlockable locations, each with `unlockAt` based on `totalEarned`), and `RARITY`. **Economy numbers here (`baseCost`, `costMult`, `rate`, `unlockAt`) are identical between v2 and v3 by design** — v3 only changes acquisition/presentation, not the underlying curve.
- **Economy math**: `costFor()` computes exponential upgrade costs (`base * mult^level`); `clickPower()` and `perSecond()` compute current income, both scaled by `locationBonusMult()` (+15% per unlocked location beyond the first).
- **Rendering**: DOM is built imperatively (no framework). `renderPanel()` dispatches to `renderClickTab()` / `renderAutoTab()` / `renderLocTab()` based on the active nav tab, rebuilding `#panel` from static data + state on every change. `buildMinerCard()` / `buildLocationCard()` construct card elements.
- **Visual effects**: floating "+N" numbers, particle bursts, ambient background particles, and a radial "portal" wipe transition on location travel (`travelTo()`). All effects respect `prefers-reduced-motion`.
- **Game loop**: `setInterval` every 200ms adds accumulated passive income; a separate interval autosaves every 5s; `beforeunload` also saves and stamps the offline-progress timestamp.
- **Locations as a theming mechanism**: switching `state.currentLocation` rewrites CSS custom properties (`--accent`, `--rockBase`, etc.) via `applyLocationVisual()`, so the rock/crystal art and ambient particles change color per-location live.

## v3-specific additions

- **Miners are gacha-only — there is no shop/buy path for `autoDefs`.** `state.gachaMiners` is the *only* source of auto-income: an array of `{defIndex, rate}`, each entry a random drop from a gacha chest with `rate` individually rolled at `autoDefs[defIndex].rate * (0.8..1.2)` (`STAT_ROLL_RANGE`). `perSecond()` just sums `state.gachaMiners`. `autoDefs` entries therefore only carry `rate`/`rarity`/flavor — no `baseCost`/`costMult`, since nothing purchases them directly (the click-power upgrade in `renderClickTab()` is the only thing still using `costFor`/resources). The Auto tab (`renderAutoTab()`/`buildCollectionCard()`) is a pure collection showcase: found defs show accumulated count/rate/individual rolls, not-yet-found defs render as a locked "???" card. `CHEST_DROP_CHANCE` (currently 0.12) is tuned as the *entire* acquisition curve now — raising it is the lever if miners ever feel too scarce, not adding a buy button back.
- **Chest/gacha flow is fully automatic, not click-gated, and never blocks clicking the ore — by design, not by accident.** `maybeDropChest()` rolls `CHEST_DROP_CHANCE` on every ore click; the chest sprite (`#chest`) must carry the `hidden` class by default in the HTML (its CSS bob animation makes a missing `hidden` class easy to miss visually during review, but it means the chest silently sits pre-spawned). It appears anchored to the screen edge (`right:min(1.5vw,6px)`, sized off `min(15vw,72px)` — those numbers are chosen to clear `#rock-wrap`'s own `min(66vw,250px)` box at any viewport width, don't shrink the ore or grow the chest without re-checking that math), bounces, and a `setTimeout(openChestNow, CHEST_AUTO_OPEN_MS)` opens it on its own — clicking the chest just calls the same `openChestNow()` early. `openChestNow()` → `openGachaFlow()`: `rollRarity()` weights outcomes via `GACHA_WEIGHTS`, then `autoDefs.findIndex(d=>d.rarity===rarity)` maps rarity straight to a def (1:1 today — if that ever changes, `rollRarity`'s def-lookup needs to become def-index-weighted instead of rarity-weighted). The reel (`#reel-track`) animates via `requestAnimationFrame` with an eased offset (`1 - (1-t)^power`, higher power for legendary), ticking a sound sample every time the floor'd item index changes. **`#gacha-overlay` itself is `pointer-events:none`** — only `.gacha-card` (edge-anchored the same way as the chest, deliberately shrunk to `min(74vw,200px)` with a `160px` reel) is clickable, so the reel spin and result card sit as a side panel over *part* of the ore on narrow phones rather than a full-screen modal; the exposed portion of `#rock-wrap` keeps taking clicks the whole time. There is no `#chest-backdrop` dimming layer any more — an earlier pass had one (plus a fully centered/blocking chest and modal gacha overlay), both were removed because they made the ore unclickable while pending.
- **Ore damage state** (`oreStage`, 0→1→2→shatter-reset) is purely a cosmetic click counter, not persisted — every click always grants `clickPower()` regardless of stage; the stage only toggles which crack `<g>` layer is visible and triggers a bigger burst + flash on the 3rd hit.
- **Two separate art systems, don't conflate them.** `generateLocationTexture(loc, size)` still supplies the ore's own small-scale rock-grain fill (canvas value-noise via seeded `mulberry32`, cached in `textureCache`, `size=220` for the SVG `<pattern>` on `#rockTextureImg`) — this one is legitimately "noisy material texture" and is unchanged. The *scene backdrop* is a completely different, separate system: `generateLocationArt(loc)` builds a hand-authored illustrated scene per location (faceted crystals for the cave, branching gold veins with nuggets, hanging/rising icicles, a network of glowing lava cracks, an asteroid+starfield for space) out of small SVG shape helpers (`svgCrystal`, `svgVein`, `svgIcicle`, `svgCrack`, `svgStarField`, `svgAsteroid`) placed with a seeded RNG for organic scatter — the randomness only decides *placement*, never pixel color, so it never degrades into abstract noise. Cached per `loc.id` in `artCache`, applied via `svgToDataUrl()` as `document.body`'s `background-image` (`cover`, no tiling) in `applyLocationVisual()`. If a location ever needs new set-dressing, extend the per-`loc.id` branch in `generateLocationArt()` — don't reach for `generateLocationTexture()`, that one is scoped to the ore.
- **Small "icon" art is also hand-authored SVG now, not pixel sprites.** `PICKAXE_ICON_URL` (the click-upgrade card icon, matches the cursor pickaxe's own path data), `gemIconUrl(loc)` (the crystal accents floating on the ore, reuses `svgCrystal`) and `minerIconUrl(rarity)` (the reel silhouette and the collection-card icon backdrop, a helmet+headlamp+pickaxe figure recolored per rarity) all replace what used to be tiny 16×16 Kenney sprite crops. The `SPRITES` object still carries the old `ore_*`/`figure_dark`/`figure_hood` base64 entries for backward compat with anything that might still reference them, but nothing in the live code reads those specific keys anymore — don't be surprised they're "unused" if you go looking.
- **The pickaxe follows the pointer instead of sitting fixed next to the rock**, on `pointer:fine` devices only (`window.matchMedia("(pointer: fine)")`, gates `document.body.classList.add("has-cursor-pickaxe")` which is what actually flips `cursor:none` on via CSS). `#pickaxeCursor` is a `position:fixed` wrapper moved by a `main`-scoped `pointermove` listener (`translate(clientX, clientY)`); the `<svg id="pickaxe">` inside it still owns the `.swing` keyframe animation exactly as before, now just riding along at cursor position. `swingPickaxe()` gates the visual swing on `pointerFine` (touch devices skip straight to the sparks/dust/sound, same as the existing `reducedMotion` branch) — the impact feedback itself is never skipped, only the cursor-pickaxe animation is.
- **Audio**: real CC0 sample playback (`playSample()`, decoded from the embedded `SOUNDS` base64 via `decodeAudioData`'d into `sampleCache`, routed through a shared generated-impulse-response `ConvolverNode` for cave reverb) replaces most of v2's oscillator-only approach; a few oscillator-based tones (`tone()`) remain for lightweight UI feedback, now routed through a lowpass filter to stay "duller" than v2's chiptune tones.
- **Ambient music is a generative music-box melody, not a static drone or a licensed track.** An early version was just 3 held oscillators crossfading between chords — it read as a hum, no melodic movement, so don't regress to that shape. The current one is two layers: `MUSIC_DRONE` (2 fixed low oscillators, `MUSIC_DRONE_VOLUME = 0.02`, started once in `startMusic()`, purely a soft floor) plus `playMelodyNote()` firing single bell-like notes (soft attack, `exponentialRampToValueAtTime` decay over ~3.4s) picked from `MUSIC_SCALE` (A minor pentatonic, two octaves) — a pentatonic scale specifically so *any* random note order still sounds intentional, never a wrong note. `scheduleNextNote()` re-arms itself with a randomized 2–4.6s gap (occasionally firing a quick second note ~0.65–1.2s later) so notes land irregularly, like a wind chime, not on a metronome. Both layers share `musicBus`/`musicMasterGain` into the same `audioCtx`/`reverbNode` as the sound effects; per-voice volumes (`MUSIC_NOTE_PEAK = 0.07`, drone at 0.02) sit well under effects (0.4–0.6) so clicks/chest/gacha stay on top. Starts lazily on the first real interaction (`startMusic()` from the `rockWrap`/`muteBtn` handlers, guarded by `musicStarted`) — never eagerly, per autoplay policy — and piggybacks on existing `state.muted`/`visibilitychange` plumbing rather than adding new: `setMusicMuted()` just ramps `musicMasterGain` between 0 and 1, and the tab-hidden handler's `audioCtx.suspend()` halts every scheduled note for free (a suspended context stops advancing `currentTime`; `setTimeout`s driving `scheduleNextNote()` keep firing in wall-clock time regardless, they just schedule silent no-ops against a paused clock until resume).
- **All third-party sprites/sounds are embedded as base64**, not fetched — `SPRITES.<name>` is a ready-to-use `data:image/png;base64,...` string assigned directly to `<img>.src`; `SOUNDS.<name>` is a raw base64 string decoded via `b64ToArrayBuffer()`. Every `<img>` (static and JS-created) still carries an `onerror` fallback (`withImgFallback()`, hides the element) as defense-in-depth, even though a corrupted embedded string is the only realistic way it'd ever fire.

When editing either version, keep everything within its single HTML file (v3's JS may be split into a sibling `.js` file if it grows unwieldy, per the file's own header comment intent, but is currently inline) — this project intentionally has no build pipeline or module system.
